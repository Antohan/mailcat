# Шаблон плана итерации (PLAN-ITER<N>.md)

> Как составлять план новой итерации. Правило №1: **план без указателей на код —
> не план**. Brainstorming (в том числе скиллом superpowers) допустим как
> черновик-генератор идей, но финальный план приводится к этому формату.

## Обязательная структура (в этом порядке)

### 1. Заголовок и статус

`# Итерация N — тема`

Строка-статус под заголовком: план активный или заморожен (история), где идут
работы (ветка), что не дополняется. Завершённый план замораживается навсегда.

### 2. Журнал решений (CHANGELOG.md)

Скопировать секцию из предыдущего плана: формат записи
(`дата · iterN:ID · тема` + Сделано / Решения / Отклонения) и правила —
запись на каждую задачу, отклонения только через журнал, молча план не менять.

### 3. Цель

2–4 строки: что изменится для пользователя и как это проверяется. Нет цели —
нет итерации.

### 4. Задачи (сердце плана)

Каждая задача:

```markdown
- [ ] **ID-Кодовое имя.** (префикс = тема: UI-N, W-N, T-N)
      Что делает: поведение пользователя/системы — измеримо и наблюдаемо.
      Затронуто: файлы и символы — точные имена функций/типов.
      Ограничения: какие инварианты «Не трогать» касаются задачи.
```

Правило спеки: **задача без указателей на код в план не попадает.** Если
неизвестно, какие символы затронет — сначала исследование в отдельной сессии,
потом задача с указателями. Одна задача = одна сессия.

### 5. Definition of Done итерации

Проверяемые утверждения «да/нет»: что должен увидеть человек в живой сессии,
что должны показать автотесты, какие регрессии недопустимы.

### 6. Правила итерации

Скопировать блок из предыдущего плана и поправить: ветка (`dev`), формат
коммитов (`iterN:UI-N: …`), circuit breaker, модели по умолчанию, CHANGELOG.

### 7. Инварианты

Что заранее известно для HANDOFF «Не трогать» по ходу итерации (напишите
сразу, если предвидите — например, новые запреты протокола).

## Чек-лист перед стартом итерации

- [ ] Каждая задача реалистично умещается в одну сессию
- [ ] У каждой задачи есть файлы/символы и ожидаемое поведение
- [ ] DoD проверяем: что руками (smoke, VPN), что автотестами
- [ ] Security-чувствительные задачи помечены (для security-reviewer)
- [ ] Секция CHANGELOG на месте; HANDOFF «Дальше» указывает на первую задачу

## Хорошо vs плохо

**Хорошо:**
`UI-2: колонки Отправитель|Тема|Дата; отправитель — t:Name с fallback на
локальную часть; дата «сегодня → HH:MM / Чт / ДД.ММ»; видна при ширине
панели ~40% (FormatMessageRow, internal/ui/mail.go, format.go)`

**Плохо:**
`Улучшить список писем` — нет ни указателей, ни поведения, ни критерия готовности.

## Если используете superpowers brainstorming

Скилл brainstorming/writing-plans — хороший генератор идей и черновика.
Но его формат (проза, дизайн-доки) — черновик: финальный план вы переносите
в этот шаблон, проверяя, что у каждой задачи есть указатели на код и
проверяемый результат. План в чужом формате агенту не скармливать.
